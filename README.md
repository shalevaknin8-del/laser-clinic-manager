# מערכת ניהול קליניקת לייזר

מערכת ניהול מלאה לקליניקת הסרת שיער בלייזר - לקוחות, תורים, קטלוג
טיפולים, חשבוניות מס, ניהול לידים, ניהול משתמשי מערכת עם הרשאות,
ו**צ'אטבוט לקוחות** לבירור תורים עם אימות זהות דו-שלבי.

נכתבה כפרויקט לימודי בקורס פייתון (לימודי חוץ, הטכניון) - פרויקט
אמצע (ניהול Entity/Manager) ופרויקט סיום (שכבת שיחה + אימות + Web
מלא) על אותה בסיס קוד.

**סביבת פרודקשן:** https://shalevaknin.pythonanywhere.com
(ראו [DEPLOY.md](DEPLOY.md) לנוהל הרצה מקומית ועדכון שרת מלא).

---

## דרכי הפעלה

למערכת שתי דרכי הפעלה שחולקות את אותו בסיס נתונים בדיוק:

- **תפריט טקסט (CLI)** - `main.py` - נקודת הכניסה המקורית מפרויקט האמצע.
- **ממשק Web** - `app.py` - שרת Flask עם שלושה משטחים:
  - `/` - ממשק ניהול גרפי לצוות הקליניקה (דורש התחברות).
  - `/login` - מסך כניסה לצוות.
  - `/chat` - צ'אטבוט פתוח ללקוחות הקצה (בלי צורך בחשבון).

## התקנה והרצה מהירה

```bash
python3 -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env
python3 -c "import secrets; print(secrets.token_hex(32))"   # להדביק כ-SECRET_KEY ב-.env
python3 migrations/run_all.py
python3 seed_data.py               # נתוני דמו - כולל תרחישי הבדיקה של הצ'אטבוט
python3 create_admin.py            # יוצר את המנהלת הראשונה
python3 app.py
```

לאחר מכן: **http://127.0.0.1:5001** (פורט 5001 ולא 5000 כי ב-macOS שירות
AirPlay Receiver תופס את 5000 כברירת מחדל).

בלי `GEMINI_API_KEY` ב-`.env` המערכת עדיין עובדת במלואה - שכבת הבנת
השפה של הצ'אטבוט עוברת אוטומטית למסלול גיבוי מבוסס regex (מדייק
פחות, אבל לא נופל). הוראות הרצה מלאות, כולל נוהל עדכון שרת
PythonAnywhere, ב-[DEPLOY.md](DEPLOY.md).

### ארכיטקטורה

הפרויקט בנוי בשכבות ברורות, כל שכבה יודעת רק על השכבה שמתחתיה:

```
entities  →  managers  →  api  →  chatbot
                            ↑
                          auth (חוצה את כל ה-api)
```

- **Entity** (`entities/`) - מחלקות פשוטות המייצגות שורה בטבלה.
- **Manager** (`managers/`) - כל שאילתת SQL נמצאת כאן ורק כאן. לכל
  ישות מנהל עם CRUD מלא + לוגיקה עסקית ייעודית (בדיקת התנגשות
  תורים, ביטול חשבונית ללא מחיקה, נעילת משתמש אחרי כישלונות וכו').
- **API** (`api/`) - Blueprints של Flask שחושפים את המנהלים כ-REST,
  בלי לגעת ב-SQL בעצמם. הרשאות נאכפות פה באמצעות `auth/decorators.py`.
- **Chatbot** (`chatbot/`) - לא נכנס דרך ה-API כלל; קורא למנהלים
  ישירות בתוך התהליך. `chatbot/verification.py` הוא שער יחיד שכל
  שליפת מידע אישי חייבת לעבור דרכו - זורק חריגה אם השיחה לא אומתה
  במלואה (שני שלבים: תעודת זהות + קוד OTP לטלפון).

## תכונות עיקריות

### ממשק ניהול (לצוות הקליניקה, מחייב התחברות)

1. **דשבורד** - תורים היום, מספר לקוחות, הכנסות החודש, לידים פתוחים.
2. **תורים** - הוספה עם בדיקת התנגשות אוטומטית, הצעת שעות פנויות,
   ותמיכה ב**טיפול מרוכב** (כמה טיפולים באותו ביקור, עם מחיר ומשך
   זמן כולל שמחושבים אוטומטית ומשפיעים על ההתנגשויות ושעות הפעילות).
3. **לקוחות** - הוספה/עריכה/מחיקה, חיפוש חי, מסך היסטוריה מלא.
4. **טיפולים** - קטלוג עם הוספה/עריכה (שינוי מחיר שמור למנהלת).
5. **חשבוניות** - הפקה עם מספור אוטומטי (`YYYY-NNNN`), וביטול/שחזור
   בלבד - **לעולם לא מחיקה**, לפי חוקי מס הכנסה.
6. **לידים** - הוספה, עדכון סטטוס, המרה ללקוח בלחיצה אחת.
7. **ניהול משתמשים ותפקידים** (מנהל/עובד) - יצירת עובדות, איפוס
   סיסמה, השבתה/הפעלה (עם הגנה על עצמי ועל המנהל האחרון), ויומן
   ביקורת (`audit_log`) לכל פעולה רגישה.
8. **הרשאות דו-רמתיות** - `admin` מול `employee`, נאכפות בשרת בכל
   בקשה (לא רק הסתרת כפתורים בממשק).

### צ'אטבוט לקוחות (`/chat`, פתוח בלי חשבון)

- זיהוי לקוחה לפי שם חלקי; שם לא ייחודי → בקשת הבהרה, לעולם לא ניחוש.
- אימות דו-שלבי לפני חשיפת כל מידע: **תעודת זהות** (מוצפנת PBKDF2,
  מושווית עם `hmac.compare_digest` נגד timing attacks) ואז **קוד
  OTP חד-פעמי** שנשלח לטלפון הרשום *במסד*, לא ליעד שהוקלד בשיחה.
- הגבלת ניסיונות בשני השלבים (`MAX_VERIFICATION_ATTEMPTS`,
  `OTP_MAX_ATTEMPTS`) ונעילה מנומסת של השיחה בלי לחשוף פרטים.
- מציג את התור האמיתי מהמסד ומתקן את הלקוחה אם היא טעתה בתאריך/שעה.
- שכבת NLU: Gemini עם סכמת Pydantic קשיחה, ומסלול גיבוי מבוסס
  regex כשאין מפתח API או שיש תקלת רשת - הבוט לעולם לא נופל.
- הגנות מפורשות: תעודת זהות מחולצת ב-regex ולעולם לא נשלחת למודל
  חיצוני; הודעת המשתמשת נעטפת כדאטה מסומן (לא הוראה) בפרומפט.

## אבטחה

- סיסמאות: `scrypt` (werkzeug). תעודות זהות וקודי OTP: PBKDF2 עם
  200,000 סיבובים ומלח ייחודי - נשמרת רק טביעת אצבע, לעולם לא הערך הגולמי.
- הגבלת קצב (`Flask-Limiter`) על נקודות קצה רגישות: התחברות, שליחת/בדיקת
  קוד, ובדיקת תעודת זהות.
- כותרות אבטחה על כל תגובה (`X-Frame-Options`, `Content-Security-Policy`,
  `X-Content-Type-Options`, `HSTS` בפרודקשן).
- `SESSION_COOKIE_HTTPONLY` + `SESSION_COOKIE_SAMESITE=Lax` +
  `SESSION_COOKIE_SECURE` (אוטומטי בפרודקשן).
- כל שאילתת SQL בפרויקט משתמשת בפרמטרים (`?`) - אין שרשור מחרוזות.
- `Config.validate()` מפיל את השרת מיד בעלייה אם `.env` מכיל הגדרה
  מסוכנת (למשל DEBUG=true בפרודקשן).

## בדיקות

בתיקיית `tests/` יש שתי שכבות בדיקה:

**בדיקות legacy** (`test_clients.py`, `test_appointments.py`,
`test_conflicts.py`, `test_invoices.py`, `test_leads.py`,
`test_treatments.py`, `test_soft_delete.py`, `test_errors.py`,
`test_error_handling.py`, `test_chat_flow.py`) - סקריפטים מפרויקט
האמצע/הסיום המוקדם, מריצים תרחיש ומדפיסים פלט לבדיקה ידנית.
**שימו לב:** חלקם כותבים ישירות ל-`data/clinic.db` (בסיס הנתונים
האמיתי) ואינם רצים תחת `pytest` (אין להם פונקציות `assert`/`test_*`
בפועל) - יש להריץ אותם בזהירות (`python3 tests/<file>.py`), לא על
מסד עם נתוני אמת.

**חבילת בדיקות חדשה (pytest, מבודדת)** - נבנתה כחלק מסבב QA מלא על
המערכת הקיימת:

| קובץ | מכיל |
|---|---|
| `tests/conftest.py` | תשתית משותפת: בסיס נתונים זמני ומבודד לגמרי מ-`data/clinic.db` (נוצר תחת `tests/_test_data/`, מאופס לפני **כל** בדיקה בודדת), פיקסצ'רות ליצירת משתמשים/לקוחות/לקוח Flask, וכיבוי בטוח של ה-rate limiter בבדיקות שלא בודקות אותו |
| `tests/test_scenarios.py` | חמשת תרחישי החובה של הצ'אטבוט מהבריף, עם תמלול שיחה קריא מודפס לכל תרחיש - כפולה כ-pytest וגם כסקריפט עצמאי (`python3 tests/test_scenarios.py`) |
| `tests/test_security.py` | הרשאות, חסימת גישה בלי התחברות, prompt injection, SQL injection, אי-דליפת `national_id_hash`, שימוש חוזר/פקיעה/ניחוש-יתר של OTP, חסימת עובד מפעולות מנהל, הגנת "מנהל אחרון"/השבתה עצמית, ובדיקת rate limiting בפועל |
| `tests/test_edge_cases.py` | פורמטים של ת"ז/טלפון, קלט קיצוני בצ'אט (ריק/ארוך/אימוג'ים/HTML), תאריך/שעה לא תקינים, לוגיקה עסקית (תפוסה, חריגה משעות פעילות, ביטול ששחרר סלוט, כמה תורים עתידיים, מחיקת לקוח עם תורים), ומצב שיחה (פקיעה, החלפת זהות, ת"ז לפני שם) |
| `tests/run_all_tests.py` | מריץ את שלוש החבילות ברצף ומדפיס סיכום PASS/FAIL |

הרצה:

```bash
python3 -m pytest tests/test_scenarios.py tests/test_security.py tests/test_edge_cases.py -v
# או:
python3 tests/run_all_tests.py
```

מצב נוכחי: **60/60 בדיקות עוברות**. פירוט מלא של הממצאים, הבאגים
שתוקנו והשורש שלהם - ראו `TEST_REPORT.md` (ראו "מה עדיין פתוח" למטה).

## מה עדיין פתוח / לא הושלם

הרשימה הזו מיועדת למי שממשיך לפתח את הפרויקט - כדי לא להניח
שמשהו כבר בוצע רק כי יש לו קובץ בשם דומה בפרויקט.

- **`TEST_REPORT.md` טרם נכתב כקובץ סופי.** סבב ה-QA שהניב את
  `tests/test_security.py` ו-`tests/test_edge_cases.py` והתיקונים
  המפורטים למטה בוצע במלואו והבדיקות עוברות (60/60), אבל מסמך
  הסיכום הפורמלי (מה נבדק / מה נמצא / מה תוקן) עדיין לא הופק כקובץ
  בפרויקט. יש לבקש את השלמתו לפני הגשה סופית.
- **עיצוב ממשק חדש (זהב-שמנת, "גלוסי") קיים אבל לא הוחל.** בקובץ
  `Laser IL ממשק חדש.zip` (בשורש הפרויקט) יש גרסה חדשה של
  `templates/login.html` ו-`templates/chat.html` בפלטת צבעים חדשה
  (`--gold`, `--cream`, `--gold-ink`...), וגם קובץ `preview_index.html`
  שהוא טיוטת מבנה/עיצוב (ללא לוגיקה) לעמוד הניהול הראשי. שלושתם
  **עדיין לא הוחלפו** בקבצי `templates/`/`static/` הפעילים באפליקציה.
  יש להשוות אותם לקבצים הקיימים, לוודא שה-id-ים וה-`data-*` שה-JS
  (`static/app.js`) מסתמך עליהם נשמרים, ואז להחליף בפועל.
- **תיקוני QA שכבר בוצעו בקוד הקיים (ולא רק בבדיקות):**
  - `api/auth_api.py` - נוסף `@auth_bp.route("/me", ...)` שהיה חסר
    לחלוטין (ה-endpoint פשוט לא היה קיים).
  - `managers/client_manager.py` - נוסף `import sqlite3` חסר ב-`set_national_id`.
  - `api/helpers.py` - `parse_treatment_ids_from_json` כבר לא זורק
    חריגה לא מטופלת על קלט לא-מספרי.
  - `utils/validators.py` - `validate_positive_integer` חדש למניעת
    קריסה על משך טיפול לא-שלם; `validate_phone` הורחב לקבל את אותם
    פורמטים ש-`normalize_phone` כבר תמך בהם (כולל `+972`).
  - `managers/appointment_treatment_manager.py` - `check_combo_conflict`
    כעת דוחה תור שחורג משעות הפעילות, גם כשאין התנגשות עם תור אחר.
  - `chatbot/nlu.py` - מסלול הגיבוי (regex) כעת מזהה גם תשובת שם
    "עירומה" בלי מילת פתיחה כמו "קוראים לי" (למשל תשובה ל"אפשר את
    השם המלא?" בשלב הבהרה בין כמה לקוחות עם אותו שם).
  - פירוט מלא, כולל תרחיש כישלון לכל אחד, מיועד ל-`TEST_REPORT.md`
    (ראו סעיף קודם).
- **ממצא נתונים ב-`seed_data.py`:** תעודת הזהות שהוזנה עבור "רותם
  כהן" (`987654325`) לא עוברת את בדיקת ספרת הביקורת הרשמית של
  תעודת זהות ישראלית - כלומר אימות זהות מלא עבור הלקוחה הזו ב-דמו
  ייכשל תמיד. תרחיש הבהרת השם (שתי "רותם") לא תלוי בזה ועדיין עובד,
  אבל אם רוצים גם להדגים אימות מלא עבורה יש להחליף למספר תקין.
- **התנהגות קיימת שנבדקה ותועדה כמכוונת, לא כבאג** (ראו הבדיקות
  המתאימות ב-`test_edge_cases.py`): המערכת לא חוסמת קביעת תור
  בתאריך עבר (יכול לשמש לתיעוד רטרואקטיבי), וטלפון בצורת קו נייח
  (9 ספרות, לא מתחיל ב-05) נדחה בכוונה כי הבוט שולח OTP ב-SMS.

`appointment_treatments` חדשה - הרחבה מעבר ל-5 הטבלאות המקוריות.
כל הלוגיקה מבודדת ב-`managers/appointment_treatment_manager.py`,
בלי לגעת ב-`schema.sql` או ב-`managers/appointment_manager.py`
המקוריים, כדי ש-`main.py` (התפריט הטקסטואלי) ימשיך לעבוד ללא שינוי.
