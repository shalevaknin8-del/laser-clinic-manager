# מערכת ניהול קליניקת לייזר

מערכת ניהול מלאה לקליניקת הסרת שיער בלייזר - לקוחות, תורים, קטלוג
טיפולים, חשבוניות מס וניהול לידים. נכתבה כפרויקט אמצע בקורס פייתון
(לימודי חוץ, הטכניון).

למערכת שתי דרכי הפעלה שחולקות את אותו בסיס נתונים בדיוק:

- **תפריט טקסט (CLI)** - `main.py` - נקודת הכניסה המקורית.
- **ממשק Web** - `app.py` - עמוד ניהול גרפי מקומי בעברית, שנבנה
  מעל אותו קוד קיים בדיוק, בלי לשנות בו שורה אחת.

---

## דרישות והתקנה

- Python 3.8 ומעלה
- Flask (רק לצורך ממשק ה-Web - התפריט הטקסטואלי לא צריך שום ספרייה חיצונית)

```bash
pip3 install flask
```

הכל רץ מקומית ואופליין לגמרי - אין קריאות רשת, אין CDN, אין תלות
בשירות חיצוני כלשהו.

---

## הרצה

### תפריט טקסט (המקורי)

```bash
python3 main.py
```

### ממשק Web

```bash
python3 app.py
```

לאחר מכן פותחים דפדפן בכתובת: **http://127.0.0.1:5001**

(הפורט 5001 ולא 5000 בכוונה - ב-macOS שירות AirPlay Receiver תופס
את פורט 5000 כברירת מחדל ומתנגש עם שרתי Flask מקומיים.)

בהרצה הראשונה, שתי נקודות הכניסה (`main.py` ו-`app.py`) יוצרות את
בסיס הנתונים אוטומטית (`data/clinic.db`) לפי `schema.sql`, ומאתחלות
קטלוג טיפולים ראשוני של 13 טיפולים אם הקטלוג ריק.

## מבנה הפרויקט

```
laser_clinic_manager/
├── main.py                    # תפריט טקסט - נקודת הכניסה המקורית
├── app.py                     # שרת Flask - ה-API של ממשק ה-Web
├── database.py                # חיבור ל-SQLite + אתחול הסכמה
├── schema.sql                 # הגדרת 5 הטבלאות המקוריות
│
├── entities/                  # מחלקות ישות (Client, Appointment, Treatment, Invoice, Lead)
├── managers/                  # שכבת הגישה לבסיס הנתונים - 5 מנהלים מקוריים
│   └── appointment_treatment_manager.py   # מנהל חדש ל"טיפול מרוכב" (ראו הערה בהמשך)
├── utils/                     # ולידציות ותרגום שגיאות SQLite לעברית
├── tests/                     # סקריפטי בדיקה ל-5 המנהלים
│
├── templates/index.html       # עמוד ה-Web היחיד (SPA)
├── static/style.css           # עיצוב
├── static/app.js              # לוגיקת צד לקוח - מחברת בין הדף ל-API
│
└── data/clinic.db             # בסיס הנתונים (נוצר אוטומטית בהרצה ראשונה)
```

### ארכיטקטורה

הפרויקט בנוי בדפוס **Entity + Manager**:

- **Entity** (`entities/`) - מחלקות פשוטות המייצגות שורה בטבלה (שדות
  + `__str__` בלבד, בלי גישה ל-DB).
- **Manager** (`managers/`) - כל הגישה לבסיס הנתונים מרוכזת כאן.
  לכל ישות מנהל עם 5 מתודות CRUD (`insert` / `get_by_id` / `get_all`
  / `update` / `delete`), בתוספת פונקציונליות עסקית ייעודית (למשל
  בדיקת התנגשות תורים, ביטול חשבונית ללא מחיקה, המרת ליד ללקוח).
- **`app.py`** הוא שכבת "מעטפת" בלבד מעל ה-Managers הקיימים - הוא לא
  כותב שאילתות SQL (למעט חריג אחד מתועד למטה) וחושף אותם כ-REST API
  שממשק ה-Web צורך.

## תכונות עיקריות (ממשק ה-Web)

1. **דשבורד** - תורים היום, מספר לקוחות, הכנסות החודש, לידים פתוחים.
2. **תורים** - טבלה, הוספה עם בדיקת התנגשות אוטומטית והצעת שעות
   פנויות, ותמיכה ב**טיפול מרוכב** - קביעת כמה טיפולים באותו ביקור
   (למשל שפם + סנטר), כשהמחיר ומשך הזמן הכולל מחושבים אוטומטית
   ומשפיעים נכון על בדיקת ההתנגשויות.
3. **לקוחות** - טבלה, הוספה/עריכה, חיפוש חי, ומסך היסטוריה (כל
   התורים והחשבוניות של לקוח נתון).
4. **טיפולים** - קטלוג עם הוספה/עריכה ואתחול קטלוג ראשוני.
5. **חשבוניות** - רשימה, הפקה עם מספור אוטומטי, וביטול (**לא מחיקה** -
   לפי חוקי מס הכנסה, חשבונית שהונפקה לעולם לא נמחקת, רק מסומנת
   כמבוטלת).
6. **לידים** - רשימה, הוספה, עדכון סטטוס, והמרה ללקוח בלחיצה אחת.

כל הטפסים כוללים ולידציה בצד לקוח עם הודעות שגיאה בעברית, הודעות
Toast להצלחה/שגיאה, ודיאלוג אישור לפני כל פעולה הרסנית (מחיקה/ביטול).
הממשק רספונסיבי ועובד גם על טאבלט.

## הערה על "טיפול מרוכב"

תכונת הטיפול המרוכב (כמה טיפולים באותו תור) דרשה טבלת קישור
`appointment_treatments` חדשה בין תורים לטיפולים - הרחבה מעבר ל-5
הטבלאות המקוריות בסכימה. כדי לא לגעת בקבצים המקוריים (`schema.sql`,
`database.py`, `managers/appointment_manager.py`), כל הלוגיקה הזאת
מבודדת לחלוטין בקובץ חדש: `managers/appointment_treatment_manager.py`.
טבלת appointments המקורית לא השתנתה, ו-`main.py` (התפריט הטקסטואלי)
ממשיך לעבוד בדיוק כמו קודם, בלי שינוי.
